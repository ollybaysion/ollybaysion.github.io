<p class="standfirst">
    에이전트에게 프롬프트를 직접 치는 대신, <strong>에이전트를 프롬프트하는
    시스템을 설계한다</strong>. 2026년 6월 Addy Osmani가 명명한 개념의 정리 —
    루프의 해부, 다섯 개의 부품과 여섯 번째 요소, 하루짜리 루프 설계 예시,
    그리고 루프가 끝내 해결하지 못하는 것.
  </p>
<div class="credits">
  <span>작성 · 2026-08-09</span>
  <span>원문 · <a href="https://addyo.substack.com/p/loop-engineering">Addy Osmani, "Loop Engineering"</a></span>
  <span>재게재 · <a href="https://www.oreilly.com/radar/loop-engineering/">O'Reilly Radar</a></span>
</div>
<section id="s1">
  <div class="sec-head"><span class="num">01</span><h2>프롬프트에서 루프로</h2></div>
  <p class="lede">지난 2년의 작업 방식은 좋은 프롬프트를 쓰고, 충분한 맥락을
    주고, 한 번에 한 턴씩 진행하는 것이었다. 이 글이 선언하는 전환은
    단순하다 — 다음 지시를 타이핑하는 사람이 되지 말고, <strong>다음 지시를
    결정하는 시스템을 만들라</strong>.</p>
  <blockquote>
    <p>코딩 에이전트에 프롬프트를 주지 마라. 에이전트에 프롬프트를 주는
      루프를 설계하라.</p>
    <cite>Peter Steinberger</cite>
  </blockquote>
  <blockquote>
    <p>더 이상 Claude에 직접 프롬프트하지 않는다. Claude에 프롬프트를 주는
      루프를 실행하고, 무엇을 할지 파악한다.</p>
    <cite>Boris Cherny — Anthropic, Claude Code</cite>
  </blockquote>
  <p>Osmani는 이 흩어진 실천들(Steinberger, Cherny)을 종합해
    <strong>loop engineering</strong>이라는 이름을 붙였다. 정의는: 목표를
    정의하고, 에이전트가 스스로 일을 찾아 실행하고, 결과를 검증하고, 완료를
    기록한 뒤 다음 일로 넘어가게 하는 <strong>자동 발견·배분·검증·의사결정
    시스템</strong>을 구축하는 일. 원문은 이것을 "재귀적 목표(recursive
    goal)"라고 부른다 — 목표를 한 번 정의하면 AI가 완료될 때까지 반복한다.</p>
</section>
<section id="s2">
  <div class="sec-head"><span class="num">02</span><h2>루프의 해부</h2></div>
  <p class="lede">루프의 최소 단위는 <strong>태스크 + 체크</strong>다.
    체크 없는 태스크는 자동화가 아니라 희망이다 — 지능은 모델에 있지만,
    <strong>신뢰성은 루프에 있다</strong>.</p>
  <div class="diagram" role="group" aria-label="루프 한 사이클">
    <div class="flow">
      <span class="node io">trigger (cron·hook·goal)</span>
      <span class="arrow">→</span>
      <span class="node">discover</span>
      <span class="arrow">→</span>
      <span class="node lead">act</span>
      <span class="arrow">→</span>
      <span class="node gate">verify</span>
      <span class="arrow">→</span>
      <span class="node">record</span>
      <span class="arrow back">↺ next</span>
    </div>
    <p class="caption">발견 → 실행 → 검증(블루 = 관문) → 기록 → 다음 사이클. 검증이 빠지면 루프가 아니라 반복 실행이다</p>
  </div>
  <p>트리거 유형으로 보면 루프는 네 갈래다(용어는 후속 정리 글들에서
    굳어진 분류).</p>
  <div class="table-scroll">
    <table class="picker">
      <thead><tr><th>유형</th><th>동작</th><th>예시</th></tr></thead>
      <tbody>
        <tr><td>heartbeat</td><td>짧은 간격으로 상시 실행</td><td>큐를 계속 비우는 워커</td></tr>
        <tr><td>cron</td><td>정해진 시각에 실행</td><td>매일 아침 이슈 트리아지</td></tr>
        <tr><td>hook</td><td>이벤트에 반응해 실행</td><td>PR 푸시·CI 실패 시 가동</td></tr>
        <tr><td>goal</td><td>성공 조건 달성까지 반복 후 종료</td><td>"test/auth 전부 통과 + 린트 클린"</td></tr>
      </tbody>
    </table>
  </div>
  <p>goal 루프에서 중요한 세부: 종료 판정은 <strong>일하는 모델이 아니라
    별도의 채점 모델</strong>이 한다. 코드를 쓴 자가 완료를 선언하지
    못하게 — 작성자와 채점자의 분리가 루프 설계의 반복 모티프다.</p>
</section>
<section id="s3">
  <div class="sec-head"><span class="num">03</span><h2>부품 다섯, 그리고 여섯 번째</h2></div>
  <p class="lede">Osmani가 꼽는 루프의 구성요소는 다섯이고, 이것들을
    지탱하는 여섯 번째가 외부 상태다.</p>
  <ul class="rules">
    <li><span class="mark">C1</span><div>
      <b>Automations — 루프의 심장</b>
      <span>일정에 따라 스스로 실행되는 발견·분류 단계. 발견이 있으면 트리아지
        인박스로, 없으면 자동 아카이브. OpenAI 내부 사용례: 일일 이슈 분류,
        CI 실패 요약, 커밋 브리프, 최근 버그 탐지.</span></div></li>
    <li><span class="mark">C2</span><div>
      <b>Worktrees — 병렬의 격리</b>
      <span>여러 에이전트가 같은 저장소를 동시에 만지면 충돌한다. git worktree로
        히스토리는 공유하되 작업 디렉토리를 분리한다. 단, 기술적 충돌은 도구가
        풀어도 <strong>병렬 수의 상한은 인간의 리뷰 대역폭</strong>이 정한다.</span></div></li>
    <li><span class="mark">C3</span><div>
      <b>Skills — 맥락의 일회 작성</b>
      <span>프로젝트 규칙·컨벤션·"과거 사건 때문에 이렇게 안 하는 이유"를
        <span class="k">SKILL.md</span>에 기록해 루프가 매 사이클 프로젝트를
        재분석하지 않게 한다. 스킬이 없으면 에이전트가 맥락 공백을 자신감 있게
        메우는 <strong>의도 부채(intent debt)</strong>가 쌓인다.</span></div></li>
    <li><span class="mark">C4</span><div>
      <b>Plugins &amp; Connectors — 실제 도구 연결</b>
      <span>MCP로 이슈 트래커·DB·스테이징 API·Slack에 접근한다. Codex와
        Claude Code가 모두 MCP를 지원하므로 커넥터는 도구를 넘어 재사용된다.
        작동하는 루프의 모습: PR 자동 오픈 → 티켓 연결 → CI 통과 후 Slack 핑.</span></div></li>
    <li><span class="mark">C5</span><div>
      <b>Sub-agents — 작성자와 검토자의 분리</b>
      <span>코드를 쓴 모델이 자기 코드를 채점하면 편향된다. 초안 에이전트와
        검증 에이전트, 필요하면 보안 리뷰 에이전트를 분리한다. 각자 토큰을
        쓰므로 <strong>신뢰가 필요한 지점에만</strong> 투자한다.</span></div></li>
    <li><span class="mark">+1</span><div>
      <b>External state — 루프의 기억 <span class="state">the sixth thing</span></b>
      <span>에이전트는 실행 사이에 전부 잊는다. 완료한 것과 다음 할 것을
        마크다운 파일이나 보드 등 대화 밖에 기록한다 — "모델은 잊지만
        저장소는 기억한다."</span></div></li>
  </ul>
  <h3>도구별 구현 대응표</h3>
  <div class="table-scroll">
    <table class="picker">
      <thead><tr><th>구성요소</th><th>Codex</th><th>Claude Code</th></tr></thead>
      <tbody>
        <tr><td>Automations</td><td>Automations 탭 + Triage 인박스</td><td><span class="k">/loop</span> · cron · lifecycle hooks · GitHub Actions</td></tr>
        <tr><td>Worktrees</td><td>내장(스레드별 워크트리)</td><td><span class="k">git worktree</span> · <span class="k">--worktree</span> · <span class="k">isolation: worktree</span></td></tr>

      </tbody>
    </table>
  </div>
</section>
<section id="s4">
  <div class="sec-head"><span class="num">04</span><h2>하루짜리 루프 — 설계 예시</h2></div>
  <p class="lede">원문이 보여주는 실제 루프 하나. 포인트는 마지막 문장이다 —
    "당신은 이 루프를 <strong>한 번</strong> 설계했다. 단계를 직접
    프롬프트하지 않았다."</p>
  <ol class="steps">
    <li><div><b>아침 자동화 실행</b>
      <span>어제의 CI 실패·열린 이슈·최근 커밋을 읽고, 트리아지 스킬로
        발견사항을 마크다운/보드에 저장한 뒤, 발견 건마다 격리된 워크트리를
        만든다.</span></div></li>
    <li><div><b>워크트리마다 서브에이전트 가동</b>
      <span>에이전트 A가 수정안을 초안하고, 에이전트 B가 프로젝트 스킬과
        기존 테스트에 대조해 검증한다.</span></div></li>
    <li><div><b>커넥터가 바깥일 처리</b>
      <span>PR을 열고, 티켓을 갱신하고, CI가 통과하면 채널에 핑한다.</span></div></li>
    <li><div><b>남은 것은 사람에게</b>
      <span>루프가 처리하지 못한 것만 트리아지 인박스로 올라온다 — 사람의
        역할이 실행에서 판정으로 이동한다.</span></div></li>
  </ol>
</section>
<section id="s5">
  <div class="sec-head"><span class="num">05</span><h2>루프가 해결하지 못하는 것</h2></div>
  <p class="lede">원문의 후반부가 이 글을 광고가 아니라 엔지니어링 문서로
    만든다. 루프는 세 가지를 해결하지 못한다.</p>
  <ul class="rules">
    <li><span class="mark">L1</span><div>
      <b>검증은 여전히 당신 책임이다</b>
      <span>무인으로 도는 루프는 실수도 무인으로 한다. 검증 서브에이전트를
        분리해도 "완료"는 <strong>주장이지 증명이 아니다</strong>.</span></div></li>
    <li><span class="mark">L2</span><div>
      <b>이해 부채(comprehension debt)</b>
      <span>루프가 쓴 코드를 읽지 않고 빠르게 배포할수록, 코드베이스의 실제
        상태와 당신의 이해 사이 간격이 벌어진다.</span></div></li>
    <li><span class="mark">L3</span><div>
      <b>인지적 항복(cognitive surrender)</b>
      <span>루프가 알아서 돌면 판단을 멈추고 결과를 그냥 받아들이고 싶은
        유혹이 생긴다. 저자의 고백: 직접 검토를 놓았다면 "지속적으로 더 깊은
        구멍을 파는 악순환"에 빠졌을 것이다.</span></div></li>
  </ul>
  <p>같은 루프를 두 사람이 돌려도 결과가 갈리는 이유가 여기 있다.</p>
  <div class="versus">
    <div>
      <span class="tag">Engineer A · 증폭</span>
      <h4>이해하는 일을 루프로 가속한다</h4>
      <p>깊이 아는 코드베이스 위에서 루프를 돌리고, 산출물을
        <span class="who">읽고 판정하는 역할을 유지</span>한다.</p>
      <dl>
        <dt>루프의 효과</dt><dd><b>속도 증폭</b> — 이해가 병목을 푼다</dd>
        <dt>부채</dt><dd>이해 부채가 쌓이지 않음</dd>
      </dl>
    </div>
    <div>
      <span class="tag">Engineer B · 회피</span>
      <h4>이해를 피하려고 루프를 쓴다</h4>
      <p>읽기 싫은 코드를 루프에 떠넘기고 <span class="who">결과만
        수용</span>한다. 겉보기 산출량은 같다.</p>
      <dl>
        <dt>루프의 효과</dt><dd><b>악순환 가속</b> — 구멍을 더 깊게 판다</dd>
        <dt>부채</dt><dd>이해 부채 + 인지적 항복 복리</dd>
      </dl>
    </div>
  </div>
  <p>루프 자체는 이 차이를 인식하지 못한다. <strong>당신이 인식해야
    한다.</strong></p>
</section>
<section id="s6">
  <div class="sec-head"><span class="num">06</span><h2>엔지니어로 남기</h2></div>
  <p class="lede">Cherny 인용의 요점은 "일이 쉬워졌다"가 아니라
    <strong>레버리지 포인트가 이동했다</strong>는 것이다. 루프 설계는
    프롬프트 엔지니어링보다 쉬운 일이 아니라 더 어려운 일이다.</p>
  <blockquote>
    <p>루프를 구축하라. 단, 단순히 실행 버튼을 누르는 사람이 아니라,
      엔지니어로 남으려는 의도로 구축하라.</p>
    <cite>Addy Osmani — Loop Engineering, 결론</cite>
  </blockquote>
  <p>저자의 균형 감각도 기록해둘 만하다: 루프를 권하지만 직접 프롬프트도
    여전히 유효하고, 토큰이 풍부한 조건과 빈약한 조건에서 패턴이 크게
    달라진다는 경고를 붙인다. 그리고 이 담론은 여기서 끝나지 않았다 —
    한 달 뒤 "루프 다음 층"을 주장하는 <strong>graph engineering</strong>이
    등장한다. 짝 문서에서 다룬다.</p>
</section>
