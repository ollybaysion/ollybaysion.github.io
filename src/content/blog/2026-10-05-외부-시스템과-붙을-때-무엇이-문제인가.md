## 외부 시스템이란

<p class="define">이 시리즈에서 외부 시스템은 <b>내 코드가 아니면서 내 코드가 기대는 것</b>이다.</p>
<ul class="chips"><li>데이터베이스</li><li>웹 프레임워크와 화면</li><li>다른 팀 · 다른 회사의 API</li><li>메시지 브로커</li></ul>

종류는 다르다. 그래도 공통 성질이 셋 있다.

<div class="traits">
<div class="trait"><span class="n">01</span>내가 고칠 수 없다.</div>
<div class="trait"><span class="n">02</span>내 일정과 상관없이 바뀐다.</div>
<div class="trait"><span class="n">03</span>내 의지와 상관없이 실패한다.</div>
</div>

아래 코드 예는 모두 같은 가상의 주문 서비스다. 이 서비스는 택배사 API 를 불러 배송을 접수하고 조회한다.

## 문제 다섯

### 01 로직이 섞인다

<p class="label"><span class="tag down">내가 하류</span>&nbsp; 증상</p>

```java
@PostMapping("/orders/{id}/ship")
public String ship(@PathVariable long id, Model model) {
    Order order = orderRepository.findById(id).orElseThrow();
    // 무료 배송 규칙이 화면 컨트롤러 안에 있다
    if (order.getTotal() >= 50_000 && !order.isIsland()) {
        order.setShippingFee(0);
    }
    model.addAttribute("order", order);
    return "order/shipped";
}
```

<p class="label">왜 곤란한가</p>

무료 배송 규칙을 시험하려면 웹 요청을 만들어야 한다. 밤마다 도는 배치나 다른 프로그램은 이 규칙을 쓸 수 없다. 규칙은 화면 코드와 함께 바뀌고 함께 깨진다.

<div class="source"><p>비즈니스 로직이 UI 코드로 스며들면 자동 테스트가 어렵다. 배치로 돌리기도, 다른 프로그램이 부르게 하기도 어렵다. 흔한 대응은 "이번에는 이 층에 로직을 넣지 않는다"는 새 층이다. 위반을 잡는 장치가 없으면 몇 년 뒤 그 층도 로직으로 어지러워진다.</p><span class="who">Alistair Cockburn · Hexagonal Architecture · 2005</span></div>

### 02 코드가 묶인다

<p class="label"><span class="tag down">내가 하류</span>&nbsp; 증상</p>

```java
public class ShippingService {
    private final JdbcTemplate jdbc;
    private final CarrierHttpClient carrier =
            new CarrierHttpClient("https://api.carrier.example");

    public void ship(long orderId) {
        Map<String, Object> row = jdbc.queryForMap(
                "SELECT * FROM orders WHERE id = ?", orderId);
        carrier.post("/v2/shipments", row);
    }
}
```

<p class="label">왜 곤란한가</p>

이 클래스는 DB 의 테이블 모양과 택배사의 URL · 버전을 직접 안다. 택배사가 v3 를 내면 이 클래스를 고친다. DB 서버가 내려가면 이 클래스를 시험할 수도 없다.

<div class="source"><p>애플리케이션이 외부 DB 에 묶여 있으면 DB 가 내려가거나 크게 바뀔 때 개발자가 일을 하지 못한다. 화면 쪽 문제와 원인이 같다. 비즈니스 로직과 외부와의 상호작용이 얽혀 있다.</p><span class="who">Alistair Cockburn · Hexagonal Architecture · 2005</span></div>

Robert C. Martin 은 반대로 목표를 적는다. DB 나 웹 프레임워크가 낡으면 "최소한의 소란으로" 갈아 끼울 수 있어야 한다. 코드가 묶여 있으면 이 목표를 이룰 수 없다(*The Clean Architecture*, 2012).

### 상류와 하류

다음 두 문제는 상류와 하류라는 말이 있어야 설명된다. Eric Evans 가 *Domain-Driven Design*(2003)에서 쓴 말이다. 두 말은 <strong>누구의 변경이 누구에게 번지는지</strong>를 나타낸다.

<div class="flow">
<div class="box up"><span class="role">상류</span><span class="name">택배사 API</span><span class="note">응답 모양을 정한다</span></div>
<div class="arrow"><span class="glyph">→</span>변경이 번진다</div>
<div class="box down"><span class="role">하류</span><span class="name">내 주문 서비스</span><span class="note">그 모양에 맞춰 고친다</span></div>
</div>
<p class="caption">판별 질문: "A 가 인터페이스를 바꾸면 B 가 고쳐야 하나?" — 그렇다면 A 가 상류다.</p>

호출 방향이나 데이터 방향과는 상관없다. 내 백엔드가 API 를 내주면 내가 상류가 된다. 이때 프런트엔드가 나를 먼저 불러도 프런트엔드가 하류다.

### 03 모델이 번진다

<p class="label"><span class="tag down">내가 하류</span>&nbsp; 증상</p>

```java
// 택배사의 응답 타입이 도메인 객체 안까지 들어왔다
public class Order {
    private CarrierTrackingResponse tracking;
}

// 택배사의 코드값이 주문 규칙의 조건이 되었다
if ("DLV_CMPL".equals(order.getTracking().getStatusCd())) {
    order.complete();
}
```

<p class="label">왜 곤란한가</p>

택배사의 이름과 코드값이 우리 팀의 말이 된다. 택배사가 `statusCd` 를 바꾸면 주문 도메인까지 고친다. interface 로 감싸도 막히지 않는다. 반환 타입이 `CarrierTrackingResponse` 이면 상대 모델은 그대로 퍼진다.

<div class="source"><p>상류 시스템과의 큰 인터페이스는 하류 모델의 의도를 끝내 덮어쓴다. 하류 모델은 그때그때 상대 모델을 닮도록 고쳐진다. 잘 설계된 상류라도 지금 프로젝트의 필요와 맞지 않을 수 있다.</p><span class="who">Eric Evans · DDD Reference · 2015 — Anticorruption Layer</span></div>

### 04 모델이 굳는다

<p class="label"><span class="tag up">내가 상류</span>&nbsp; 증상</p>

```java
@GetMapping("/api/orders/{id}")
public Order order(@PathVariable long id) {
    // 도메인 객체를 그대로 JSON 으로 낸다
    return orderRepository.findById(id).orElseThrow();
}
```

<p class="label">왜 곤란한가</p>

이제 `Order` 의 필드가 곧 API 계약이다. 바깥 사용자가 그 모양에 기대기 시작한다. 내부 필드 이름 하나를 바꾸려 해도 바깥 사용자를 함께 고쳐야 한다. 앞의 세 문제와 방향이 반대다. 이번에는 내 변경이 남에게 번진다.

<div class="source"><p>도메인 모델을 데이터 교환 언어로 쓰면 그 모델은 사실상 굳는다. 그러면 새 개발 요구에 응하지 못한다.</p><span class="who">Eric Evans · DDD Reference · 2015 — Published Language</span></div>

### 05 실패가 옮는다

<p class="label"><span class="tag down">내가 하류</span>&nbsp; 증상</p>

```java
@GetMapping("/orders/{id}")
public OrderView order(@PathVariable long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    // 타임아웃을 정하지 않았다. 택배사가 응답하지 않으면 이 요청은 기다리기만 한다
    TrackingResponse t = restTemplate.getForObject(
            CARRIER_URL + order.getInvoiceNo(), TrackingResponse.class);
    return OrderView.of(order, t);
}
```

<p class="label">왜 곤란한가</p>

택배사가 느려지면 이 요청을 처리하는 스레드가 하나씩 묶인다. 스레드가 바닥나면 택배와 상관없는 화면도 응답하지 않는다. 메모리 안의 호출에는 이런 일이 없다. 그래서 외부 호출을 메모리 안의 호출처럼 다루면 이 문제는 운영 중에야 드러난다.

<div class="source"><p>원격 호출은 실패할 수 있다. 또는 타임아웃이 올 때까지 응답 없이 멈출 수 있다. 응답 없는 공급자 하나에 호출자가 많이 걸리면 중요한 자원이 바닥난다. 그 결과 여러 시스템에 걸친 연쇄 장애가 생긴다.</p><span class="who">Martin Fowler · CircuitBreaker · 2014</span></div>

## 다섯 문제의 공통 원인

다섯 문제는 모양이 다르다. 이 시리즈는 다섯 문제를 같은 원인으로 본다. 바뀌는 것과 바뀌지 않아야 하는 것이 경계 없이 한곳에 있다.

<div class="flow">
<div class="box keep"><span class="role">바뀌지 않아야 하는 것</span><span class="name">내 규칙</span><span class="note">무료 배송 기준 · 주문 완료 조건</span></div>
<div class="wall"></div>
<div class="box"><span class="role">바뀌는 것</span><span class="name">외부</span><span class="note">화면 · DB · 택배사 API · 내가 내준 API 의 모양</span></div>
</div>
<p class="caption">점선이 경계다. 2화부터 다룰 아이디어는 모두 이 선을 어디에, 어떻게 세울지에 대한 답이다.</p>

이 생각은 새것이 아니다. David Parnas 는 1972년 논문에서 모듈을 나누는 기준을 이렇게 제안했다. 어렵거나 바뀔 가능성이 큰 설계 결정의 목록에서 시작한다. 그리고 모듈마다 그런 결정 하나를 다른 모듈에게서 숨긴다. Parnas 가 같은 논문에서 든 바뀔 결정의 첫째는 <strong>입력 형식(input format)</strong>이다. 외부 시스템이 주는 데이터의 모양이 바로 그런 결정이다. Parnas 의 말로 하면 다섯 문제는 숨겨야 할 결정이 드러나 있는 상태다.
