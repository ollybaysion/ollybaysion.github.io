이 시리즈는 외부 시스템과 연동할 때 생기는 문제와, 그 문제를 풀려고 나온 아키텍처
아이디어를 다룬다. 층 구조 · 의존 역전 · Hexagonal · Clean Architecture ·
Anti-Corruption Layer 같은 이름은 모두 어떤 문제에 대한 답이다. 그런데 이름부터
배우면 답만 외우고 문제는 놓치기 쉽다.

그래서 1화는 해법을 다루지 않는다. 무엇이 문제인지만 정의한다. 문제마다 그 문제를
처음 글로 적은 원전의 문장을 함께 든다.

## 외부 시스템이란

이 시리즈에서 외부 시스템은 **내 코드가 아니면서 내 코드가 기대는 것**이다.

- 데이터베이스
- 웹 프레임워크와 화면(UI)
- 다른 팀이나 다른 회사가 운영하는 API
- 메시지 브로커

종류는 달라도 공통 성질이 셋 있다.

1. 내가 고칠 수 없다.
2. 내 일정과 상관없이 바뀐다.
3. 내 의지와 상관없이 실패한다.

이 성질은 새로운 발견이 아니다. David Parnas 는 1972년 논문에서 모듈을 나누는 기준을
이렇게 제안했다.

> We propose instead that one begins with a list of difficult design decisions or
> design decisions which are likely to change. Each module is then designed to hide
> such a decision from the others.

어렵거나 바뀔 가능성이 큰 설계 결정의 목록에서 시작하라는 말이다. 그리고 모듈마다 그런
결정 하나를 다른 모듈에게서 숨기라고 한다. Parnas 가 같은 논문에서 든 "바뀔 가능성이
큰 결정"의 첫 번째는 **입력 형식(input format)**이다. 외부 시스템이 주는 데이터의
모양이 바로 그런 결정이다.

## 먼저 상류와 하류

외부 시스템과의 관계를 말할 때는 상류(upstream)와 하류(downstream)라는 말을 쓴다.
Eric Evans 가 *Domain-Driven Design*(2003)에서 쓴 말이다. 이 두 말은 **누구의 변경이
누구에게 번지는지**를 나타낸다.

- **상류**: 모델과 인터페이스를 정해서 내주는 쪽이다. 상류가 바뀌면 하류가 따라 고친다.
- **하류**: 그것을 가져다 쓰는 쪽이다. 하류가 바뀌어도 상류는 그대로다.

판별법은 질문 하나다. "A 가 인터페이스를 바꾸면 B 가 고쳐야 하나?" 답이 "그렇다"면
A 가 상류고 B 가 하류다.

| 관계 | 인터페이스를 정하는 쪽 | 상류 | 하류 |
| --- | --- | --- | --- |
| 프런트엔드 ↔ 내 백엔드 | 백엔드(API 계약) | 백엔드 | 프런트엔드 |
| 내 백엔드 ↔ 결제사 API | 결제사(응답 모양) | 결제사 | 백엔드 |

헷갈리기 쉬운 점이 셋 있다.

1. **호출 방향과 다르다.** 프런트엔드가 백엔드를 먼저 부르지만 프런트엔드가 하류다.
2. **데이터 방향과 다르다.** 데이터는 양쪽으로 흐른다. 계약을 정하는 쪽은 하나다.
3. **계층의 안팎과 다르다.** 상류 · 하류는 시스템이나 팀 사이의 관계다. 한 애플리케이션
   안의 층 구분이 아니다.

이 시리즈의 문제는 대부분 내가 하류일 때 생긴다. 마지막 문제 하나만 내가 상류일 때
생긴다.

## 문제 다섯

### 로직이 섞인다

비즈니스 규칙이 외부와 맞닿는 코드에 섞인다. 화면 코드나 DB 접근 코드 안에 계산과
판단이 들어간다.

Alistair Cockburn 은 Hexagonal Architecture 원문(2005)을 이 문제로 시작한다. 비즈니스
로직이 UI 코드로 스며들면 피해가 셋이라고 적는다.

1. 시험할 로직이 필드 크기나 버튼 위치 같은 자주 바뀌는 화면 세부에 묶인다. 그래서
   자동 테스트를 돌리기 어렵다.
2. 같은 이유로 사람이 쓰던 시스템을 배치로 돌리기 어렵다.
3. 같은 이유로 다른 프로그램이 이 시스템을 부르게 하기 어렵다.

흔한 대응도 적었다. 새 층을 만들고 "이번에는 정말 이 층에 로직을 넣지 않는다"고
약속한다. 그런데 위반을 잡는 장치가 없으면 몇 년 뒤 그 층도 로직으로 어지러워진다.

### 코드가 묶인다

내 코드가 외부 시스템의 구현에 직접 기댄다. 그러면 외부가 멈추거나 바뀔 때 내 코드도
같이 멈추거나 바뀐다.

Cockburn 은 같은 글에서 반대편, 곧 DB 쪽 문제도 적는다. 애플리케이션 로직이 외부 DB 에
묶여 있으면 DB 서버가 내려가거나 크게 바뀔 때 개발자가 일을 하지 못한다. 그는 이것을
화면 쪽 문제와 같은 원인에서 나온 것으로 본다. 비즈니스 로직과 외부와의 상호작용이
얽힌 것이다.

Robert C. Martin 은 2012년 글에서 반대로 목표를 적는다. 데이터베이스나 웹 프레임워크
같은 외부가 낡으면 "최소한의 소란으로" 갈아 끼울 수 있어야 한다. 코드가 묶여 있으면
이 목표를 이룰 수 없다.

### 모델이 번진다

외부 시스템의 개념 · 이름 · 코드값이 내 코드 곳곳으로 퍼진다. 처음에는 연동 코드에만
있다. 시간이 지나면 서비스와 도메인 코드까지 들어온다.

Evans 는 이것을 "오염(corruption)"이라고 부른다. 그가 정리한 *DDD Reference*(2015)는
이렇게 적는다.

> A large interface with an upstream system can eventually overwhelm the intent of
> the downstream model altogether, causing it to be modified to resemble the other
> system's model in an ad hoc fashion.

상류의 큰 인터페이스가 하류 모델의 의도를 덮어쓴다는 말이다. 하류 모델은 그때그때
상류 모델을 닮도록 고쳐진다. Evans 는 레거시만의 문제로 보지 않는다. 잘 설계된 상류라도
지금 프로젝트의 필요에 맞지 않을 수 있다고 적는다.

이 문제는 interface 하나로 막히지 않는다. interface 는 호출 모양을 맞춘다. 그런데 그
인자와 반환 타입이 상대의 타입이면 상대 모델은 그대로 퍼진다.

### 실패가 옮는다

외부 시스템의 장애가 내 시스템의 장애가 된다.

Martin Fowler 는 2014년 글에서 이 문제를 이렇게 적는다. 원격 호출은 실패할 수 있다.
또는 타임아웃이 올 때까지 응답 없이 멈출 수 있다. 응답 없는 공급자 하나에 호출자가
많이 걸려 있으면 중요한 자원이 바닥난다. 그 결과 여러 시스템에 걸친 연쇄 장애가 생긴다.

메모리 안의 호출에는 이런 일이 없다. 그래서 외부 호출을 메모리 안의 호출처럼 다루면
이 문제가 숨어 있다가 운영 중에 드러난다.

### 내가 상류가 되면 모델이 굳는다

앞의 넷은 내가 하류일 때의 문제다. 반대로 내가 API 를 내주는 상류일 때도 문제가 있다.

내 도메인 모델을 그대로 API 응답으로 내보낸다고 하자. 그러면 바깥의 사용자가 그 모양에
기대기 시작한다. 이제 내부 필드 하나를 바꾸려 해도 바깥 사용자를 함께 고쳐야 한다.
*DDD Reference* 는 이렇게 적는다.

> If one is used as a data interchange language, it essentially becomes frozen and
> cannot respond to new development needs.

도메인 모델을 데이터 교환 언어로 쓰면 그 모델이 굳어서 새 요구에 응하지 못한다는 말이다.

## 다섯 문제의 공통 원인

다섯 문제는 모양이 다르다. 하지만 이 시리즈는 다섯 문제를 같은 원인으로 본다. 바뀌는
것(외부)과 바뀌지 않아야 하는 것(내 규칙)이 경계 없이 한곳에 있다는 것이다. Parnas 의
말로 하면 숨겨야 할 결정이 드러나 있다.

2화부터 다룰 아키텍처 아이디어는 모두 이 경계를 어디에, 어떻게 세울지에 대한 답이다.

## 시리즈 지도

2화부터 5화는 이어지는 흐름이다. 앞 해법이 남긴 문제를 다음 해법이 받는다. 6화부터는
같은 목적 아래의 다른 문제를 하나씩 다룬다.

| 회차 | 문제 | 해법 | 원전 |
| --- | --- | --- | --- |
| 2 | 로직이 섞인다 | 층 구조(Layered Architecture) | — |
| 3 | 위층이 아래층 구현에 묶인다 | 의존 역전 원칙 | Robert C. Martin, 1996 |
| 4 | 층 사이 선이 지켜지지 않고 로직이 샌다 | Hexagonal Architecture(포트와 어댑터) | Alistair Cockburn, 2005 |
| 5 | 비슷한 안팎 구조가 여럿 따로 나온다 | Onion → Clean Architecture | Jeffrey Palermo, 2008 · Robert C. Martin, 2012 |
| 6 | 모델이 번진다 | Anti-Corruption Layer | Eric Evans, 2003 |
| 7 | 내가 상류가 되면 모델이 굳는다 | DTO · Published Language | Martin Fowler, 2002 · Eric Evans, 2003 |
| 8 | 실패가 옮는다 | Timeout · Circuit Breaker · Bulkhead | Michael Nygard, 2007 |
