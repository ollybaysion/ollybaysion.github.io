<section id="s1">
  <div class="sec-head"><span class="num">01</span><h2>먼저 용어부터: 워크플로우와 에이전트는 다르다</h2></div>
  <p class="lede">
    업계는 둘을 뭉뚱그려 "에이전트"라 부르지만, 이 글은 명확히 나눈다.
    통제권이 <strong>코드에 있는가, 모델에 있는가</strong>가 기준이다.
    둘을 통칭할 때만 <span class="k">agentic system</span>이라 부른다.
  </p>
  <div class="versus">
    <div>
      <span class="tag">Workflow</span>
      <h4>워크플로우</h4>
      <p>LLM과 도구가 <strong>미리 정해진 코드 경로</strong>를 따라 오케스트레이션되는 시스템.
         흐름을 결정하는 주체는 <span class="who">개발자가 짠 코드</span>다.</p>
      <dl>
        <dt>통제</dt><dd>실행 전에 고정</dd>
        <dt>강점</dt><dd>예측 가능성 · 일관성 · 낮은 비용</dd>
        <dt>적합</dt><dd>잘 정의된 작업</dd>
      </dl>
    </div>
    <div>
      <span class="tag">Agent</span>
      <h4>에이전트</h4>
      <p>LLM이 <strong>스스로 자기 프로세스와 도구 사용을 지시</strong>하며, 과제를 어떻게 달성할지에 대한
         통제권을 쥐는 시스템. 흐름은 <span class="who">런타임에 모델</span>이 정한다.</p>
      <dl>
        <dt>통제</dt><dd>실행 중 모델이 결정</dd>
        <dt>대가</dt><dd>높은 지연시간 · 높은 비용</dd>
        <dt>적합</dt><dd>스텝 수를 모르는 열린 문제</dd>
      </dl>
    </div>
  </div>
</section>
<!-- 02 -->
<section id="s2">
  <div class="sec-head"><span class="num">02</span><h2>복잡도는 필요가 입증될 때만 한 칸씩 올린다</h2></div>
  <p>
    글 전체를 관통하는 원칙이다. 에이전트는 성능을 얻는 대신 지연시간과 비용을 지불하는
    <strong>교환</strong>이며, 그 교환이 값어치 있는지 먼저 따져야 한다.
    아래는 실제로 올라가야 할 순서다 — 아래 칸이 명백히 부족할 때만 다음 칸으로 간다.
  </p>
  <div class="ladder">
    <div class="rung">
      <span class="step">1↑</span>
      <div>
        <b>단일 LLM 호출을 먼저 최적화한다</b>
        <span>검색(retrieval)과 맥락 예시 몇 개를 붙이는 것으로 많은 경우 충분하다.
              평가(eval)를 갖추고 프롬프트를 다듬는 편이 대개 이득이 크다.</span>
      </div>
    </div>
    <div class="rung">
      <span class="step">2↑</span>
      <div>
        <b>흐름이 예측 가능하면 워크플로우로</b>
        <span>하위 작업이 무엇인지 미리 알 수 있다면 코드로 고정하라.
              일관성과 디버깅 가능성을 공짜로 얻는다.</span>
      </div>
    </div>
    <div class="rung">
      <span class="step">3↑</span>
      <div>
        <b>경로를 하드코딩할 수 없을 때만 에이전트로</b>
        <span>유연성과 모델 주도 판단이 <em>대규모로</em> 필요할 때에 한한다.
              여기서부터는 신뢰와 가드레일의 문제가 된다.</span>
      </div>
    </div>
  </div>
</section>
<!-- 03 -->
<section id="s3">
  <div class="sec-head"><span class="num">03</span><h2>프레임워크는 시작점이 아니다</h2></div>
  <p>
    Claude Agent SDK, AWS의 Strands Agents SDK, Rivet(드래그앤드롭 GUI),
    Vellum(GUI 워크플로우) 같은 도구들은 LLM 호출·도구 정의·툴 파싱 같은 표준 작업을 쉽게 해준다.
    문제는 그 대가다.
  </p>
  <p>
    추상화 레이어가 <strong>실제 프롬프트와 응답을 가려 디버깅을 어렵게 만들고</strong>,
    단순하면 될 것을 복잡하게 만들도록 유혹한다. 개발자들이 프레임워크 내부에 대한
    잘못된 가정 때문에 버그를 만드는 경우를 자주 봤다는 것이 이 경고의 근거다.
  </p>
  <p>
    권고는 <strong>LLM API를 직접 쓰는 것부터 시작하라</strong>는 것.
    프레임워크를 쓰더라도 그 밑의 코드를 이해하고 쓸 것.
  </p>
</section>

<section id="s4">
  <div class="sec-head"><span class="num">04</span><h2>기본 블록: 증강된 LLM</h2></div>
  <p>
    아래 모든 패턴의 최소 단위. <strong>LLM + 검색 + 도구 + 메모리</strong>이며,
    모델이 스스로 검색 쿼리를 만들고, 도구를 고르고, 무엇을 기억할지 정한다.
  </p>
  <div class="diagram">
    <div class="flow">
      <span class="node io">입력</span>
      <span class="arrow">→</span>
      <span class="node lead">LLM</span>
      <span class="arrow">⇄</span>
      <span class="branch">
        <span class="node">retrieval</span>
        <span class="node">tools</span>
        <span class="node">memory</span>
      </span>
      <span class="arrow">→</span>
      <span class="node io">출력</span>
    </div>
    <p class="caption">augmented llm — 증강은 모델이 스스로 호출한다</p>
  </div>
  <p>
    두 가지에 집중할 것. ① 자기 유스케이스에 맞게 증강 기능을 <strong>맞춤화</strong>할 것,
    ② 모델에게 <strong>명확한 인터페이스</strong>를 제공할 것.
    서드파티 도구 연결은 MCP(Model Context Protocol)로 표준화할 수 있다.
  </p>
</section>

<section id="s5">
  <div class="sec-head"><span class="num">05</span><h2>워크플로우 5패턴</h2></div>
  <p class="lede">
    이 다섯은 순서가 아니라 <strong>메뉴</strong>다. 각 카드의 태그는 그 패턴의 제어 흐름 모양이며,
    그것이 곧 선택 기준이 된다.
  </p>
  <div class="patterns">
    <!-- P1 -->
    <article class="pattern">
      <div class="sig">
        <span class="shape">순차</span>
        <h3>프롬프트 체이닝</h3>
        <span class="en">Prompt Chaining</span>
      </div>
      <p>작업을 <strong>고정된 순차 단계</strong>로 쪼개고, 각 호출이 앞 단계 출력을 입력으로 받는다.
         중간에 프로그래밍적 <strong>게이트</strong>를 두어 진행 상태를 검증하고, 미달이면 중단하거나 되돌린다.</p>
      <div class="diagram">
        <div class="flow">
          <span class="node io">입력</span>
          <span class="arrow">→</span>
          <span class="node">LLM 1</span>
          <span class="arrow">→</span>
          <span class="node gate">gate</span>
          <span class="arrow">→</span>
          <span class="node">LLM 2</span>
          <span class="arrow">→</span>
          <span class="node io">출력</span>
        </div>
        <p class="caption">게이트에서 걸리면 되돌아가거나 종료</p>
      </div>
      <ul class="plain">
        <li>마케팅 카피를 생성한 뒤, 다른 언어로 번역</li>
        <li>문서 개요를 쓰고 → 기준 충족을 검증한 뒤 → 본문 전체를 작성</li>
      </ul>
      <dl class="fit">
        <dt>쓸 때</dt>
        <dd>고정된 하위 작업으로 깔끔히 분해되고, <b>지연시간보다 정확도가 중요할 때</b>.
            각 호출을 쉬운 작업으로 만들어 정확도를 사고, 총 지연시간을 낸다.</dd>
      </dl>
    </article>
    <!-- P2 -->
    <article class="pattern">
      <div class="sig">
        <span class="shape">분기</span>
        <h3>라우팅</h3>
        <span class="en">Routing</span>
      </div>
      <p>입력을 <strong>분류</strong>해 서로 다른 전문화된 후속 처리로 보낸다.
         관심사가 분리되므로 각 경로의 프롬프트를 개별 최적화할 수 있다 —
         한 프롬프트에 전부 밀어넣으면 한쪽을 고칠 때 다른 쪽이 망가진다.</p>
      <div class="diagram">
        <div class="flow">
          <span class="node io">입력</span>
          <span class="arrow">→</span>
          <span class="node gate">router</span>
          <span class="arrow">→</span>
          <span class="branch">
            <span class="node">일반 문의</span>
            <span class="node">환불</span>
            <span class="node">기술 지원</span>
          </span>
          <span class="arrow">→</span>
          <span class="node io">출력</span>
        </div>
        <p class="caption">분류는 llm이 해도, 전통적 분류기가 해도 된다</p>
      </div>
      <ul class="plain">
        <li>고객 문의를 유형별로 나눠 각기 다른 프로세스로 전달</li>
        <li>쉬운 질문은 <span class="k">Haiku 4.5</span>로, 어려운 질문은 <span class="k">Sonnet 4.5</span>로
            보내 비용과 속도를 최적화</li>
      </ul>
      <dl class="fit">
        <dt>쓸 때</dt>
        <dd>구분되는 카테고리가 실제로 존재하고, <b>분류를 정확히 할 수 있을 때</b>.
            분류가 틀리면 그 아래 전부가 틀린다.</dd>
      </dl>
    </article>
    <!-- P3 -->
    <article class="pattern">
      <div class="sig">
        <span class="shape">동시</span>
        <h3>병렬화</h3>
        <span class="en">Parallelization</span>
      </div>
      <p>여러 LLM을 동시에 돌리고 출력을 프로그래밍적으로 합친다. 두 가지 변형이 있으며,
         쓰는 이유가 서로 다르다.</p>
      <div class="diagram">
        <div class="flow">
          <span class="node io">입력</span>
          <span class="arrow">→</span>
          <span class="branch">
            <span class="node">LLM A</span>
            <span class="node">LLM B</span>
            <span class="node">LLM C</span>
          </span>
          <span class="arrow">→</span>
          <span class="node gate">집계</span>
          <span class="arrow">→</span>
          <span class="node io">출력</span>
        </div>
        <p class="caption">sectioning = 서로 다른 일 / voting = 같은 일 여러 번</p>
      </div>
      <h3>Sectioning — 독립 하위 작업으로 나누기</h3>
      <ul class="plain">
        <li>가드레일: 한 인스턴스는 사용자 질의에 응답하고, 다른 인스턴스는 동시에 부적절 콘텐츠를 스크리닝</li>
        <li>자동 평가: 각 호출이 서로 다른 평가 항목 하나씩만 담당</li>
      </ul>
      <h3>Voting — 같은 작업을 여러 번 돌리기</h3>
      <ul class="plain">
        <li>코드 취약점 리뷰를 서로 다른 프롬프트 여러 개로 검사</li>
        <li>콘텐츠 유해성 판정 시 투표 임계값을 조절해 위양성·위음성 균형 맞추기</li>
      </ul>
      <dl class="fit">
        <dt>쓸 때</dt>
        <dd>속도를 위해 나눌 수 있거나, 여러 관점으로 <b>신뢰도</b>를 올려야 할 때.
            고려사항이 여럿 얽힌 작업은 각 LLM이 하나에만 집중할 때 성능이 좋다.</dd>
      </dl>
    </article>
    <!-- P4 -->
    <article class="pattern">
      <div class="sig">
        <span class="shape">위임</span>
        <h3>오케스트레이터 – 워커</h3>
        <span class="en">Orchestrator-Workers</span>
      </div>
      <p>중앙 LLM이 작업을 <strong>동적으로 분해</strong>하고 워커 LLM들에게 위임한 뒤 결과를 종합한다.
         병렬화와의 결정적 차이는 <strong>하위 작업이 미리 정해져 있지 않다</strong>는 점 —
         오케스트레이터가 입력을 보고 그때그때 정한다.</p>
      <div class="diagram">
        <div class="flow">
          <span class="node io">입력</span>
          <span class="arrow">→</span>
          <span class="node lead">orchestrator</span>
          <span class="arrow">→</span>
          <span class="branch">
            <span class="node">worker</span>
            <span class="node">worker</span>
            <span class="node">worker …</span>
          </span>
          <span class="arrow back">↩</span>
          <span class="node lead">synthesize</span>
          <span class="arrow">→</span>
          <span class="node io">출력</span>
        </div>
        <p class="caption">워커의 개수와 역할이 런타임에 결정된다</p>
      </div>
      <ul class="plain">
        <li>여러 파일에 걸친 복잡한 코드 변경</li>
        <li>여러 출처에서 정보를 모아 분석해야 하는 검색 작업</li>
      </ul>
      <dl class="fit">
        <dt>쓸 때</dt>
        <dd>어떤 하위 작업이 <b>몇 개나 필요한지 예측할 수 없는</b> 복잡한 작업.</dd>
      </dl>
    </article>
    <!-- P5 -->
    <article class="pattern">
      <div class="sig">
        <span class="shape">루프</span>
        <h3>평가자 – 최적화자</h3>
        <span class="en">Evaluator-Optimizer</span>
      </div>
      <p>한 LLM이 응답을 생성하고, 다른 LLM이 <strong>평가와 피드백</strong>을 제공하는 루프를 반복한다.</p>
      <div class="diagram">
        <div class="flow">
          <span class="node io">입력</span>
          <span class="arrow">→</span>
          <span class="node lead">generator</span>
          <span class="arrow">→</span>
          <span class="node gate">evaluator</span>
          <span class="arrow back">↺ 피드백</span>
          <span class="arrow">→</span>
          <span class="node io">합격 시 출력</span>
        </div>
        <p class="caption">합격 판정이 날 때까지 피드백을 물고 돈다</p>
      </div>
      <ul class="plain">
        <li>뉘앙스가 중요한 문학 번역 — 번역자가 처음 놓친 미묘함을 평가자가 지적</li>
        <li>여러 라운드에 걸쳐 정보를 모아야 하는 복잡한 검색</li>
      </ul>
      <dl class="fit">
        <dt>판별법</dt>
        <dd>두 질문에 모두 예스일 때만 쓴다.
            <b>①</b> 사람이 피드백을 주면 결과가 눈에 띄게 좋아지는가?
            <b>②</b> LLM이 그만한 피드백을 줄 수 있는가?</dd>
      </dl>
    </article>
  </div>

<section id="s6">
  <div class="sec-head"><span class="num">06</span><h2>자율 에이전트</h2></div>
  <p>
    사용자의 명령이나 대화로 시작해 과제가 명확해지면 <strong>독립적으로 계획하고 작동</strong>하며,
    필요하면 사람에게 되돌아와 정보를 요청하거나 판단을 구한다.
  </p>
  <p>
    핵심은 <strong>환경 피드백 루프</strong>다. 매 단계마다 도구 호출 결과나 코드 실행 결과 같은
    실제 근거를 얻어 진척도를 판단한다. 체크포인트나 막힌 지점에서 사람이 개입할 수 있고,
    보통 최대 반복 횟수 같은 정지 조건으로 통제한다.
  </p>
  <div class="diagram">
    <div class="flow">
      <span class="node io">명령 · 대화</span>
      <span class="arrow">→</span>
      <span class="node lead">plan</span>
      <span class="arrow">→</span>
      <span class="node">act (tool)</span>
      <span class="arrow">→</span>
      <span class="node gate">환경 피드백</span>
      <span class="arrow back">↺</span>
      <span class="node io">정지 조건 · 사람 개입</span>
    </div>
    <p class="caption">구현 자체는 단순하다 — 루프 안에서 도구를 쓰는 llm</p>
  </div>
  <p>
    그래서 <strong>도구 세트와 그 문서를 명확하고 신중하게 설계하는 것이 결정적으로 중요</strong>하다.
    예시로는 SWE-bench 과제를 푸는 코딩 에이전트(여러 파일 편집), Claude가 컴퓨터를
    직접 조작하는 computer-use 레퍼런스 구현이 있다.
  </p>
  <dl class="fit">
    <dt>쓸 때</dt>
    <dd>스텝 수를 예측할 수 없고 고정 경로를 하드코딩할 수 없는 <b>열린 문제</b>.
        대신 오류가 누적될 수 있으므로 <b>샌드박스 환경에서의 광범위한 테스트와 가드레일이 필수</b>다.</dd>
  </dl>
</section>
<!-- 07 -->
<section id="s7">
  <div class="sec-head"><span class="num">07</span><h2>실제로 잘 맞는 두 영역</h2></div>
  <p>부록에서 꼽은, 지금까지 특히 유망하다고 판명된 응용 영역이다.</p>
  <div class="cases">
    <div class="case">
      <h3>고객 지원</h3>
      <p>익숙한 챗 인터페이스와 도구 연동이 자연스럽게 맞물린다.</p>
      <ul class="plain">
        <li>대화는 자연스럽게 흐르면서도 외부 정보 접근이 필요하다</li>
        <li>고객 데이터·주문 이력·지식베이스를 도구로 연결</li>
        <li>환불 같은 액션을 프로그래밍적으로 실행</li>
        <li>성공을 <strong>"해결됨"으로 명확히 측정</strong> 가능 — 일부 회사는 해결 건에만 과금하는
            사용량 기반 가격제를 쓴다</li>
      </ul>
    </div>
    <div class="case">
      <h3>코딩 에이전트</h3>
      <p>잠재력이 특히 큰 영역. 이유는 피드백 루프의 질에 있다.</p>
      <ul class="plain">
        <li>코드 정답은 <strong>테스트로 자동 검증</strong>된다</li>
        <li>에이전트가 테스트 결과를 피드백 삼아 반복한다</li>
        <li>문제 공간이 잘 정의되고 구조화되어 있다</li>
        <li>품질을 객관적으로 측정할 수 있다</li>
        <li>현재 구현들은 SWE-bench Verified의 실제 GitHub 이슈를 PR 설명만 보고 해결하지만,
            <strong>시스템 정렬을 위해 사람 리뷰는 여전히 필수</strong></li>
      </ul>
    </div>
  </div>
</section>
<!-- 08 -->
<section id="s8">
  <div class="sec-head"><span class="num">08</span><h2>도구도 프롬프트 엔지니어링의 대상이다</h2></div>
  <p>
    에이전트 논의는 전체 프롬프트에만 쏠리지만, <strong>도구 정의에도 같은 수준의 주의</strong>가 필요하다.
    사람에게 좋은 UI를 설계하듯 모델에게 좋은 인터페이스를 설계하라는 뜻에서
    이를 <strong>ACI(Agent-Computer Interface)</strong>라 부른다.
  </p>
  <h3>포맷을 고를 때</h3>
  <ul class="rules">
    <li><span class="mark">01</span><div><b>생각할 토큰 여유를 줄 것</b>
      모델이 스스로를 궁지로 몰아넣기 전에 "생각"할 공간이 있어야 한다.</div></li>
    <li><span class="mark">02</span><div><b>자연스러운 형태에 가깝게</b>
      인터넷 텍스트에서 실제로 등장하는 포맷일수록 모델이 잘 다룬다.</div></li>
    <li><span class="mark">03</span><div><b>포맷팅 오버헤드를 제거할 것</b>
      줄 수 세기, 문자열 이스케이핑 같은 부담을 모델에게 지우지 말 것.</div></li>
  </ul>
  <h3>인터페이스를 다듬을 때</h3>
  <ul class="rules">
    <li><span class="mark">04</span><div><b>모델 입장에서 볼 것</b>
      설명과 파라미터만 보고 이 도구를 어떻게 쓸지 자명한가?</div></li>
    <li><span class="mark">05</span><div><b>주니어 개발자용 docstring 쓰듯</b>
      파라미터 이름과 설명을 그 수준의 친절함으로 다듬는다.</div></li>
    <li><span class="mark">06</span><div><b>워크벤치에서 많이 굴려볼 것</b>
      모델이 실제로 어떤 실수를 하는지 관찰하고 그걸 고친다.</div></li>
    <li><span class="mark">07</span><div><b>포카요케(poka-yoke) 원칙</b>
      인자 구조 자체를 바꿔 실수를 <em>불가능</em>하게 만든다.</div></li>
  </ul>
  <p>
    실제 사례가 이 절의 요지를 압축한다. SWE-bench 에이전트를 만들 때
    <strong>전체 프롬프트보다 도구 최적화에 더 많은 시간</strong>을 썼다.
    모델이 디렉터리를 옮긴 뒤 상대 경로에서 계속 실수하는 것을 발견하고
    <strong>절대 경로만 받도록 강제</strong>했더니, 그 오류가 완전히 사라졌다.
  </p>
</section>
