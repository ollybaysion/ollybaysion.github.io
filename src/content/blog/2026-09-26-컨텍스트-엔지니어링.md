<section id="s1">
  <div class="sec-head"><span class="num">01</span><h2>프롬프트 엔지니어링에서 컨텍스트 엔지니어링으로</h2></div>
  <p class="lede">
    두 용어는 대체 관계가 아니라 <strong>포함 관계</strong>다. 차이를 만드는 건 대상이 아니라
    <strong>얼마나 자주 결정하는가</strong>다.
  </p>
  <div class="versus">
    <div>
      <span class="tag">Prompt Engineering</span>
      <h4>프롬프트 엔지니어링</h4>
      <p>최적의 결과를 얻기 위해 <strong>LLM 지시문을 쓰고 조직하는</strong> 것.</p>
      <dl>
        <dt>성격</dt><dd><span class="who">이산적(discrete)</span> — 한 번 쓰면 끝</dd>
        <dt>대상</dt><dd>프롬프트 한 장</dd>
      </dl>
    </div>
    <div>
      <span class="tag">Context Engineering</span>
      <h4>컨텍스트 엔지니어링</h4>
      <p>LLM 추론 중에 <strong>최적의 토큰(정보) 집합을 큐레이션하고 유지하는</strong> 전략의 총체.</p>
      <dl>
        <dt>성격</dt><dd><span class="who">순환적(cyclical)</span> — 모델에 무엇을 넘길지 정하는 매 시점</dd>
        <dt>대상</dt><dd>시스템 프롬프트 · 도구 · 예시 · 메시지 히스토리 전부</dd>
      </dl>
    </div>
  </div>
  <p class="after-versus">
    차이가 생기는 이유는 에이전트가 여러 추론 턴에 걸쳐 작동하면서
    <strong>스스로 데이터를 계속 만들어내기</strong> 때문이다. 그렇게 불어나는 데이터를
    주기적으로 정제해야 하므로, 프롬프트 한 장을 잘 쓰는 것으로는 감당되지 않는다.
  </p>
</section>
<!-- 02 -->
<section id="s2">
  <div class="sec-head"><span class="num">02</span><h2>컨텍스트는 유한한 자원이다</h2></div>
  <blockquote>
    <p>컨텍스트 윈도우의 토큰 수가 늘어날수록, 모델이 그 컨텍스트에서
       정보를 정확히 회수하는 능력은 떨어진다.</p>
    <cite>context rot — 컨텍스트 부패</cite>
  </blockquote>
  <p>
    인간의 작업기억이 유한하듯, 언어 모델도 대량의 컨텍스트를 파싱할 때 끌어다 쓰는
    <strong>주의 예산(attention budget)</strong>을 갖고 있다.
  </p>
  <div class="decay">
    <div class="decay-bar"></div>
    <div class="decay-axis">
      <span>짧은 컨텍스트 · 높은 회수 정밀도</span>
      <span>긴 컨텍스트 · 낮은 회수 정밀도</span>
    </div>
    <p class="note">
      딱딱한 절벽이 아니라 <b>성능 기울기(performance gradient)</b>다.
      모델은 여전히 작동하지만, 정보 회수 정확도와 장거리 추론의 정밀도가
      점진적으로 떨어진다.
    </p>
  </div>
  <h3>왜 그런가 — 세 가지 구조적 이유</h3>
  <ul class="rules">
    <li><span class="mark">01</span><div><b>트랜스포머의 n² 관계</b>
      모든 토큰이 전체 컨텍스트의 모든 토큰에 attend할 수 있으므로,
      n개 토큰은 <span class="k">n²</span>개의 쌍 관계를 만든다. 길어질수록 이 관계를 제대로 포착하기 어려워진다.</div></li>
    <li><span class="mark">02</span><div><b>학습 데이터 분포</b>
      짧은 시퀀스가 긴 시퀀스보다 훨씬 흔하다 — 긴 컨텍스트는 상대적으로 덜 학습된 영역이다.</div></li>
    <li><span class="mark">03</span><div><b>위치 인코딩 보간</b>
      더 긴 컨텍스트를 가능하게 하지만, 그 대가로 열화를 동반한다.</div></li>
  </ul>
  <p>
    그래서 <strong>컨텍스트 윈도우가 커지기만 기다리는 건 답이 아니다.</strong>
    어떤 크기의 윈도우든 오염과 정보 관련성 문제를 겪는다.
  </p>
</section>
<!-- 03 -->
<section id="s3">
  <div class="sec-head"><span class="num">03</span><h2>좋은 컨텍스트의 해부</h2></div>
  <h3>시스템 프롬프트 — 골디락스 존</h3>
  <p>두 가지 실패 모드 사이에서 균형을 잡아야 한다.</p>
  <div class="triptych">
    <div>
      <span class="zone">실패 모드 A</span>
      <h4>너무 구체적 · 경직됨</h4>
      <p>복잡하고 깨지기 쉬운 로직을 하드코딩 → 취약성과 유지보수 부담.</p>
    </div>
    <div class="mid">
      <span class="zone best">골디락스 존</span>
      <h4>구체적이면서 유연하게</h4>
      <p>행동을 효과적으로 안내할 만큼 구체적이되, 모델에게 강력한 <strong>휴리스틱</strong>을 줄 만큼 유연할 것.</p>
    </div>
    <div>
      <span class="zone">실패 모드 B</span>
      <h4>너무 모호함</h4>
      <p>원하는 출력의 구체적 신호를 주지 못하거나, 공유되지 않은 맥락이 있다고 착각.</p>
    </div>
  </div>
  <ul class="plain">
    <li><strong>섹션을 명확히 구분</strong> — XML 태그나 Markdown 헤더로:
        <span class="k">&lt;background_information&gt;</span> <span class="k">&lt;instructions&gt;</span>
        <span class="k">## Tool guidance</span> <span class="k">## Output description</span></li>
    <li><strong>가장 좋은 모델 + 최소한의 프롬프트로 시작</strong>한 뒤, 초기 테스트에서 발견한
        <strong>실패 모드에 근거해서만</strong> 지시를 추가</li>
    <li>목표는 <strong>기대 행동을 온전히 서술하는 최소한의 정보 집합</strong></li>
  </ul>
  <h3>도구 — 에이전트와 세계 사이의 계약</h3>
  <p>
    도구는 <strong>에이전트와 그 정보·행동 공간 사이의 계약</strong>이며,
    토큰 효율과 에이전트의 효율적 행동 유도를 동시에 만족해야 한다.
  </p>
  <ul class="plain">
    <li>기능 <strong>중복을 최소화</strong>할 것</li>
    <li>각 도구는 <strong>자기 완결적이고, 오류에 강건하며, 용도가 극도로 명확</strong>할 것</li>
    <li>입력 파라미터는 <strong>서술적이고 모호하지 않게</strong></li>
    <li><strong>최소 실행 가능 도구 집합</strong>을 큐레이션하면 컨텍스트의 유지·가지치기가 훨씬 신뢰성 있어진다</li>
  </ul>
  <blockquote>
    <p>인간 엔지니어가 어떤 상황에 어떤 도구를 써야 할지 확답할 수 없다면,
       AI 에이전트가 그보다 잘하리라 기대할 수 없다.</p>
    <cite>비대한 도구 세트를 피하라</cite>
  </blockquote>
  <h3>예시 — 빨래 목록이 아니라 정전(canonical)</h3>
  <p>
    <strong>엣지 케이스를 빨래 목록처럼 프롬프트에 쑤셔넣고 싶은 유혹에 저항할 것.</strong>
    대신 기대 행동을 효과적으로 보여주는 <strong>다양하고 정전에 해당하는 예시 몇 개</strong>를 고른다.
    LLM에게 예시는 <strong>"천 마디 말에 해당하는 그림"</strong>이다.
  </p>
  <dl class="fit">
    <dt>관통 원칙</dt>
    <dd>모든 구성요소에 걸쳐 — <b>정보성은 높게, 그러나 빡빡하게(informative, yet tight).</b></dd>
  </dl>
</section>

<section id="s4">
  <div class="sec-head"><span class="num">04</span><h2>Just-in-Time 검색 — 미리 넣지 말고 그때 가져와라</h2></div>
  <p class="lede">
    이 글은 에이전트를 실용적으로 이렇게 정의한다:
    <strong>"루프 안에서 자율적으로 도구를 쓰는 LLM."</strong>
    그렇다면 필요한 정보는 루프 안에서 가져오면 된다.
  </p>
  <div class="versus">
    <div>
      <span class="tag">Pre-load</span>
      <h4>사전 처리 방식</h4>
      <p>관련 데이터를 <strong>미리 전부 처리해</strong> 컨텍스트에 넣어둔다(임베딩 기반 검색 등).</p>
      <dl>
        <dt>장점</dt><dd>빠르다</dd>
        <dt>약점</dt><dd>색인이 낡는다 · 컨텍스트를 미리 소모한다</dd>
      </dl>
    </div>
    <div>
      <span class="tag">Just-in-Time</span>
      <h4>그때그때 로드</h4>
      <p>에이전트는 <strong>가벼운 식별자</strong>(파일 경로, 저장된 쿼리, 웹 링크)만 들고 있다가,
         런타임에 도구로 <strong>필요한 것만 동적으로 로드</strong>한다.</p>
      <dl>
        <dt>장점</dt><dd>컨텍스트를 아낀다 · 항상 최신</dd>
        <dt>약점</dt><dd>느리다 · 설계가 어설프면 헤맨다</dd>
      </dl>
    </div>
  </div>
  <div class="diagram">
    <div class="flow">
      <span class="node io">과제</span>
      <span class="arrow">→</span>
      <span class="node lead">식별자만 보유</span>
      <span class="arrow">→</span>
      <span class="branch">
        <span class="node">glob / grep</span>
        <span class="node">targeted query</span>
        <span class="node">head / tail</span>
      </span>
      <span class="arrow">→</span>
      <span class="node gate">필요한 조각만 로드</span>
      <span class="arrow back">↺ 탐색 반복</span>
    </div>
    <p class="caption">claude code — 전체 데이터를 컨텍스트에 올리지 않고 대용량을 분석한다</p>
  </div>
  <p>
    이건 <strong>인간의 인지 방식과 같다.</strong> 우리는 전체 자료를 암기하지 않고,
    파일 시스템·받은편지함·북마크 같은 <strong>외부 조직화·색인 체계</strong>를 만들어두고
    필요할 때 꺼내 쓴다.
  </p>
  <h3>메타데이터가 곧 신호다</h3>
  <p>
    파일 계층, 명명 규칙, 타임스탬프 자체가 정보다. 예를 들어
    <span class="k">tests/test_utils.py</span> 와
    <span class="k">src/core_logic/test_utils.py</span> 는
    <strong>이름과 위치만으로 용도가 다르다는 것을 알 수 있다.</strong>
  </p>
  <h3>점진적 공개 (Progressive Disclosure)</h3>
  <p>
    런타임 탐색을 통해 에이전트는 관련 컨텍스트를 <strong>점진적으로 발견</strong>한다.
    매 상호작용이 단서를 남긴다 — 파일 크기는 복잡도를, 명명 규칙은 목적을,
    타임스탬프는 관련성을 시사한다. 에이전트는 <strong>이해를 층층이 쌓아가며
    작업기억에는 필요한 것만 남긴다.</strong>
  </p>
  <h3>하이브리드가 현실적인 답</h3>
  <p>
    많은 효과적 에이전트는 <strong>일부는 속도를 위해 미리 넣고, 나머지는 재량껏 자율 탐색</strong>한다.
    Claude Code가 정확히 이 형태다 — <span class="k">CLAUDE.md</span>는 앞단에 그냥 넣어두고,
    <span class="k">glob</span>·<span class="k">grep</span> 같은 원시 도구로 환경을 탐색해
    파일을 just-in-time으로 가져온다. 그럼으로써 <strong>색인이 낡는 문제와 복잡한 구문 트리 문제를 우회</strong>한다.
  </p>
  <dl class="fit">
    <dt>무게 배분</dt>
    <dd>과제에 달렸다. 덜 동적인 영역(법률·금융)은 하이브리드가 유리하다.
        다만 <b>모델 능력이 향상될수록 설계는 "똑똑한 모델이 똑똑하게 행동하도록 두고,
        인간의 큐레이션은 점점 줄이는" 방향</b>으로 갈 것.</dd>
  </dl>
</section>

<section id="s5">
  <div class="sec-head"><span class="num">05</span><h2>장기 과제를 위한 세 가지 기법</h2></div>
  <p class="lede">
    수십 분에서 수 시간에 걸친 연속 작업에는 별도 기법이 필요하다.
    각 카드의 태그는 그 기법이 <strong>컨텍스트에 무엇을 하는지</strong>를 가리킨다.
  </p>
  <div class="patterns">
    <!-- T1 -->
    <article class="pattern">
      <div class="sig">
        <span class="shape">압축</span>
        <h3>컴팩션</h3>
        <span class="en">Compaction</span>
      </div>
      <p>
        컨텍스트 한계에 다가가는 대화를 <strong>요약하고, 그 요약으로 새 컨텍스트 윈도우를 재시작</strong>한다.
        Claude Code에서는 메시지 히스토리를 모델에게 넘겨 가장 중요한 세부를 요약·압축한다.
      </p>
      <div class="split">
        <div class="keep">
          <span class="lbl">보존</span>
          <ul>
            <li>아키텍처 결정</li>
            <li>미해결 버그</li>
            <li>구현 세부</li>
          </ul>
        </div>
        <div class="drop">
          <span class="lbl">폐기</span>
          <ul>
            <li>중복된 도구 출력</li>
            <li>불필요한 메시지</li>
          </ul>
        </div>
      </div>
      <p>
        <strong>난점은 "무엇을 남기고 무엇을 버릴지"의 선택</strong>이다.
        지나치게 공격적인 컴팩션은 미묘하지만 결정적인 맥락을 잃게 만든다.
      </p>
      <h3>튜닝 순서</h3>
      <ul class="plain">
        <li>복잡한 에이전트 트레이스에서 컴팩션 프롬프트를 정성껏 조율한다</li>
        <li><strong>먼저 재현율(recall)을 최대화</strong> — 관련 정보를 하나도 빠뜨리지 않게</li>
        <li><strong>그다음 반복하며 정밀도(precision)를 올린다</strong> — 군더더기 제거</li>
        <li>가장 쉬운 수확: 히스토리 깊숙이 들어간 <strong>도구 호출 결과 비우기</strong>
            (Anthropic이 <strong>tool result clearing</strong>으로 플랫폼에 출시)</li>
      </ul>
      <dl class="fit">
        <dt>쓸 때</dt>
        <dd>광범위한 주고받기가 필요해 <b>대화 흐름의 연속성</b>이 중요한 과제.</dd>
      </dl>
    </article>
    <!-- T2 -->
    <article class="pattern">

  <div class="sec-head"><span class="num">06</span><h2>관통하는 원칙</h2></div>
  <p>
    컨텍스트 엔지니어링은 LLM으로 무언가를 만드는 방식의 <strong>근본적 전환</strong>이다.
    모델 능력이 커질수록 과제는 완벽한 프롬프트를 짜는 것이 아니라,
    <strong>매 단계에서 모델의 유한한 주의 예산에 어떤 정보를 넣을지 사려 깊게 큐레이션하는 것</strong>이 된다.
  </p>
  <blockquote>
    <p>원하는 결과가 나올 확률을 최대화하는,
       가장 작은 고신호(high-signal) 토큰 집합을 찾아라.</p>
    <cite>Effective Context Engineering for AI Agents</cite>
  </blockquote>
  <p>
    컴팩션을 구현하든, 토큰 효율적인 도구를 설계하든, 자율 탐색을 가능하게 하든 —
    지침이 되는 원칙은 위 한 문장이다. 그리고 모델이 개선되어 지시적 엔지니어링이 덜 필요해지더라도,
    <strong>컨텍스트를 귀하고 유한한 자원으로 다루는 것은 신뢰할 수 있는 에이전트를 만드는 데
    계속 중심에 남을 것</strong>이다.
  </p>
  <h3>앞 글과 이어보면</h3>
  <ul class="plain">
    <li>「Building Effective Agents」의 <strong>ACI(도구 설계)</strong>가 여기서는
        <strong>"도구는 최소 실행 가능 집합으로"</strong>라는 컨텍스트 관점으로 확장된다</li>
    <li>거기서의 <strong>자율 에이전트 루프</strong>가 여기서는
        <strong>just-in-time 검색 + 컴팩션 · 노트 · 서브에이전트</strong>로 구체화된다</li>
    <li>거기서의 <strong>오케스트레이터-워커</strong>는 여기서 <strong>컨텍스트 격리 장치</strong>로
        다시 해석된다 — 구조가 아니라 토큰 예산의 관점에서</li>
  </ul>
