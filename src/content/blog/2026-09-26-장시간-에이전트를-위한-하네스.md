      <section id="s1">
        <div class="sec-head"><span class="num">01</span><h2>하네스란 무엇인가</h2></div>
        <p class="lede">
          <strong>하네스</strong>는 모델이 <strong>여러 개의 컨텍스트 윈도우에 걸쳐 일관된 진척을 내도록</strong>
          떠받치는 구조화된 시스템이다. 이 글에서의 구체적 실체는
          <strong>Claude Agent SDK + 전문화된 프롬프트 + 구조화된 워크플로</strong>의 조합이다.
        </p>
        <blockquote>
          <p>교대 근무하는 엔지니어들과 같다 — 새로 투입되는 엔지니어는
             이전 교대조의 기억을 전혀 갖고 있지 않다.</p>
          <cite>컨텍스트 윈도우 단절의 비유</cite>
        </blockquote>
        <p>
          핵심은 <strong>컴팩션만으로는 부족하다</strong>는 인식이다. 컴팩션은 하나의 긴 대화를
          압축해 이어가는 기법이지만, 여러 세션에 걸친 다중 윈도우 작업에서는 그것만으로 충분하지 않다.
          기억을 대화 안이 아니라 <strong>대화 바깥의 산출물에 남겨야</strong> 한다.
        </p>
        <div class="diagram">
          <div class="flow">
            <span class="node io">컨텍스트 #1</span>
            <span class="arrow">→</span>
            <span class="branch">
              <span class="node gate">features.json</span>
              <span class="node gate">git history</span>
              <span class="node gate">progress notes</span>
            </span>
            <span class="arrow">→</span>
            <span class="node io">컨텍스트 #2 (기억 없음)</span>
            <span class="arrow back">↺ 반복</span>
          </div>
          <p class="caption">기억은 대화가 아니라 디스크 위의 산출물이 운반한다</p>
        </div>
      </section>
      <!-- 02 -->
      <section id="s2">
        <div class="sec-head"><span class="num">02</span><h2>실제로 관찰된 두 가지 실패 모드</h2></div>
        <p>
          하네스 없이 장시간 작업을 시켰을 때 나타난 실패는 방향이 정반대인 두 가지였다.
          즉 <strong>"더 하게 만들기"나 "덜 하게 만들기" 한쪽으로는 풀리지 않는다.</strong>
        </p>
        <div class="versus">
          <div>
            <span class="tag">Failure A · 과욕</span>
            <h4>한 번에 너무 많이 벌린다</h4>
            <p>여러 기능을 동시에 건드리다가
               <strong>절반만 구현되고 문서화도 안 된 기능</strong>을 남긴다.
               다음 세션은 <span class="who">무슨 일이 있었는지 추측하고 그 피해를 복구하는 데</span> 시간을 쓴다.</p>
          </div>
          <div>
            <span class="tag">Failure B · 성급함</span>
            <h4>완료를 조기 선언한다</h4>
            <p>진행 상황의 일부만 보고 <strong>프로젝트가 끝났다고 판단</strong>해
               진짜 완료 전에 작업을 멈춘다.</p>
          </div>
        </div>
        <h3>그리고 검증의 공백</h3>
        <p>
          명시적으로 지시하지 않으면 Claude는 <strong>코드를 고치기는 하지만,
          그 기능이 엔드투엔드로 동작하지 않는다는 사실은 알아채지 못하는</strong> 경향을 보였다.
          코드만 봐서는 드러나지 않는 버그가 그대로 남는다.
        </p>
      </section>
      <!-- 03 -->
      <section id="s3">
        <div class="sec-head"><span class="num">03</span><h2>이니셜라이저 에이전트 — 딱 한 번 실행되는 준비 담당</h2></div>
        <p class="lede">
          하네스는 두 종류의 에이전트로 나뉜다. <strong>이니셜라이저</strong>는 프로젝트 시작 시
          <strong>한 번만</strong> 돌면서, 이후 모든 세션이 딛고 설 발판을 만든다.
        </p>
        <div class="triptych">
          <div>
            <span class="zone">setup</span>
            <h4>init.sh</h4>
            <p>개발 환경을 띄우는 스크립트. 매 세션마다 <strong>"이 코드를 어떻게 실행·테스트하지"를 알아내는 토큰을 아낀다.</strong></p>
          </div>
          <div>
            <span class="zone">memory</span>
            <h4>claude-progress.txt</h4>
            <p>에이전트의 활동을 기록하는 진행 로그. 다음 세션이 상태를 빠르게 파악하는 통로.</p>
          </div>
          <div>
            <span class="zone">baseline</span>
            <h4>초기 git 커밋</h4>
            <p>기준 상태를 문서화. 이후 문제가 생긴 변경을 되돌릴 수 있는 지점이 된다.</p>
          </div>
        </div>
        <h3>그리고 기능 목록 (JSON)</h3>
        <p>
          가장 중요한 산출물은 <strong>기능 목록</strong>이다. 각 항목은 설명과
          <span class="k">"passes": false</span> 상태 표시를 갖는다.
          이것이 "다 끝났다"는 성급한 선언을 막는 <strong>객관적인 완료 기준</strong>이 된다.
        </p>
        <pre class="code">{
  <span class="key">"category"</span>:    <span class="str">"functional"</span>,
  <span class="key">"description"</span>: <span class="str">"New chat button creates a fresh conversation"</span>,
  <span class="key">"passes"</span>:      <span class="flag">false</span>
}</pre>
        <div class="diagram">
          <div class="flow">
            <span class="node lead">이니셜라이저 (1회)</span>
            <span class="arrow">→</span>
            <span class="branch">
              <span class="node">init.sh</span>
              <span class="node">claude-progress.txt</span>
              <span class="node">초기 커밋</span>
              <span class="node">features.json (200+)</span>
            </span>
            <span class="arrow">→</span>
            <span class="node io">이후 모든 코딩 세션</span>
          </div>
          <p class="caption">준비 비용을 한 번만 지불하고, 모든 세션이 그것을 상속한다</p>
        </div>
        <blockquote>
          <p>테스트를 삭제하거나 수정하는 것은 허용되지 않는다 —
             기능이 누락되거나 버그를 안은 채 남을 수 있기 때문이다.</p>
          <cite>이니셜라이저가 심어두는 규칙</cite>
        </blockquote>
      </section>
      <!-- 04 -->
      <section id="s4">
        <div class="sec-head"><span class="num">04</span><h2>코딩 에이전트 — 한 세션에 한 기능</h2></div>
        <p>
          이후 매 세션에 투입되는 코딩 에이전트는 전문화된 프롬프트를 받는다. 세 가지가 핵심이다.
        </p>
        <ul class="rules">
          <li><span class="mark">01</span><div><b>세션당 기능 하나에만 집중</b>
            원문이 <strong>"에이전트가 한 번에 너무 많이 하려는 성향을 다루는 데 결정적"</strong>이라고 표현한 지점.
            실패 모드 A를 직접 겨냥한다.</div></li>
          <li><span class="mark">02</span><div><b>서술적인 메시지를 단 구조화된 커밋</b>
            문제가 된 변경을 되돌릴 수 있게 만든다. 즉 커밋은 기록이자 <strong>롤백 지점</strong>이다.</div></li>
          <li><span class="mark">03</span><div><b>진행 파일에 요약 남기기</b>
            다음 세션으로의 인수인계를 성립시킨다.</div></li>
        </ul>
        <h3>인수인계를 지탱하는 세 가지 산출물</h3>
        <ul class="plain">
          <li><strong>기능 목록</strong> — JSON으로 추적되는 200개 이상의 개별 기능</li>
          <li><strong>git 히스토리</strong> — 복구와 맥락 파악을 가능하게 한다</li>
          <li><strong>진행 문서</strong> — 새 컨텍스트 윈도우로 시작한 에이전트가
              <strong>작업 상태를 빠르게 파악</strong>하게 해준다</li>
        </ul>
      </section>
      <!-- 05 -->
      <section id="s5">
        <div class="sec-head"><span class="num">05</span><h2>모든 세션이 반드시 거치는 시작 시퀀스</h2></div>
        <p class="lede">
          여기서 순서는 장식이 아니다. <strong>새 코드를 쓰기 전에 현재 상태를 확인하고
          실제로 돌려보는 것</strong>이 순서상 앞에 와야 실패 모드 B가 막힌다.
        </p>
        <ol class="steps">
          <li><div><b>작업 디렉터리 확인</b><span><span class="k">pwd</span> 로 지금 어디에 있는지부터 확정한다.</span></div></li>
          <li><div><b>git 로그와 진행 파일 검토</b><span>이전 교대조가 무엇을 했는지 읽는다.</span></div></li>
          <li><div><b>우선순위가 가장 높은 미완료 기능 선택</b><span>기능 목록에서 <span class="k">passes: false</span> 인 항목 중 하나를 고른다.</span></div></li>
          <li><div><b><span class="k">init.sh</span> 실행</b><span>개발 서버를 띄운다. 실행 방법을 매번 알아낼 필요가 없다.</span></div></li>
          <li><div><b>새 구현 전에 엔드투엔드 동작 테스트</b><span>기존 기능이 정말 동작하는지 먼저 확인한다 — 이것이 "다 됐다"는 착각을 깬다.</span></div></li>
        </ol>
        <div class="diagram">
          <div class="flow">
            <span class="node io">세션 시작</span>
            <span class="arrow">→</span>
            <span class="node gate">상태 파악</span>
            <span class="arrow">→</span>
            <span class="node gate">현행 동작 검증</span>
            <span class="arrow">→</span>
            <span class="node lead">기능 1개 구현</span>
            <span class="arrow">→</span>
            <span class="node gate">자기 검증</span>
            <span class="arrow">→</span>
            <span class="node io">커밋 · 진행 기록</span>
          </div>
          <p class="caption">검증이 앞뒤로 두 번 — 시작할 때와 끝낼 때</p>
        </div>
      </section>
      <!-- 06 -->
      <section id="s6">
        <div class="sec-head"><span class="num">06</span><h2>검증 도구를 쥐여주는 것의 효과</h2></div>
        <p>
          <strong>테스트 도구를 제공한 것이 성능을 극적으로 끌어올렸다.</strong>
          코드만 봐서는 드러나지 않는 버그를 에이전트가 스스로 찾아 고칠 수 있게 됐기 때문이다.
        </p>
        <p>
          구체적으로는 <strong>Puppeteer MCP</strong>를 통한 브라우저 자동화를 붙여,
          에이전트가 <strong>사람 사용자가 하듯이</strong> 기능을 직접 확인하게 했다.
        </p>
        <dl class="fit">
          <dt>일반화</dt>
          <dd>이 절의 요지는 Puppeteer가 아니라 —
              <b>에이전트가 자기 작업 결과를 실제로 관찰할 수 있는 통로를 만들어 주라는 것</b>이다.
              앞선 시리즈에서 말한 "환경 피드백"이 장시간 작업에서 취하는 형태다.</dd>
        </dl>
        <h3>사례 — Claude.ai 클론</h3>
        <p>
          이 하네스를 검증한 주 사례는 풀스택 웹 애플리케이션 구축이었다.
        </p>
        <ul class="plain">
          <li><strong>200개 이상</strong>의 추적되는 기능</li>
          <li>Puppeteer 기반 <strong>브라우저 엔드투엔드 테스트</strong></li>
          <li>여러 컨텍스트 윈도우에 걸친 <strong>점진적 개발</strong></li>
          <li>JSON 기반 <strong>기능 명세</strong></li>
        </ul>
      </section>

      <!-- 08 -->
      <section id="s8">
        <div class="sec-head"><span class="num">08</span><h2>남은 질문</h2></div>
        <p>
          원문은 열린 문제를 명시한다.
          <strong>범용 코딩 에이전트 하나가 모든 맥락에서 가장 잘하는지, 아니면 멀티에이전트 구조가
          더 나은 성능을 내는지는 아직 불분명하다.</strong>
        </p>
        <ul class="plain">
          <li>전문화 후보: <strong>테스트 에이전트, QA 에이전트, 코드 정리 에이전트</strong></li>
          <li>웹 개발을 넘어 <strong>과학 연구나 금융 모델링</strong> 같은 영역으로의 일반화는 아직 미탐색</li>
        </ul>
        <h3>시리즈로 이어보면</h3>
        <ul class="plain">
          <li><strong>① Building Effective Agents</strong> — 에이전트를 <em>어떤 구조로</em> 만들 것인가
              (워크플로우 5패턴, 자율 에이전트 루프, ACI)</li>
          <li><strong>② Effective Context Engineering</strong> — 매 순간 <em>무엇을 보여줄</em> 것인가
              (주의 예산, just-in-time, 컴팩션 · 노트 · 서브에이전트)</li>
          <li><strong>③ 이 글</strong> — 컨텍스트가 <em>끊긴 다음에도</em> 어떻게 계속 일하게 할 것인가
              (산출물 기반 인수인계, 강제된 시작 시퀀스, 자기 검증)</li>
        </ul>
        <p>
          ②의 "구조화된 노트 작성"이 여기서 <span class="k">claude-progress.txt</span> +
